# Launcher3 shortcut reliability implementation report

## Status and scope

An integrated implementation candidate is present on `fix/preserve-unavailable-shortcuts`, based on authoritative Google revision `c612e6ece389f21c40f8cb9cd9a4b44239f00009` (`android17-release`). It is not a fully platform-validated fix: this standalone Windows checkout has Soong definitions but no Android platform dependency tree, generated flag/Dagger classes, Soong build runner, or directly runnable canonical Launcher3 test environment. No APK, full application compilation, device result, emulator result, Gerrit submission, or upstream acceptance is claimed.

Only ordinary `Favorites.ITEM_TYPE_APPLICATION` favorites are protected by the new recovery policy, including desktop, dock, and folder children. Corrupt intents, removed profiles, widgets, deep shortcuts, promise/restore placeholders, and invalid placement remain on their existing specialized paths. Ordinary applications with positive internal-storage AND exact-row history outside recovery retain normal missing-target policy; migration targets without sufficient exact-row history are provisionally preserved.

## Integrated behavior

- The actual receiver regression reproduced a synthetic uninstall after boot completion. The receiver now emits only availability/unavailability hints; boot completion is not uninstall evidence.
- `WorkspaceAvailabilityStore` keeps versioned, checksummed per-serial/package storage evidence and database/serial/item/component-scoped recovery/removal state in no-backup storage. Writes fsync a sibling and atomically replace the committed file. Incomplete siblings are ignored; corrupt/missing/unreadable metadata cannot authorize a negative-lookup purge. Positive loader observations are batched; protection, temporary-unavailability, and uninstall evidence bypass batching.
- A one-row companion identity table gives each favorites database incarnation a token. It does not alter favorites columns or bump the existing database schema version. An existing explicit database reset drops this companion identity so reused IDs cannot inherit old tombstones. Actual SQLite behavior is covered by added canonical tests, not by the boundary fixture.
- Real package callbacks are registered on the existing helper executor. Consequential events are journaled before model work can be discarded. Active loaders restart; event revisions are checked under the same owner lock before committing loader deletions and before repository/legacy binding publication. Already loaded models use normal update tasks and retain the same item object.
- Confirmed uninstall snapshots actual ordinary favorites, rather than a package-wide tombstone that could match a new installation's rows. Reconciliation never inserts or recreates favorites and is idempotent across process death between journal and favorites writes. Lookup-based removals have a distinct task-factory entry point; preserved items are updated through the existing data-model notification mechanism.
- Loader and update paths retain the exact intent/component during recovery, retain occupied cells and folder contents, and reactivate only the saved target. Recovery does not enqueue installation icons or insert a new row. Independent disabled bits survive a storage recovery update; normal non-recovery updates and explicit suspension/profile callbacks retain their existing authority.
- Ordinary favorites can read saved icon blobs; unavailable items bypass grouped generic icon replacement and package-cache purges. Valid cached appearance is retained when recovery completes. Folder children are loaded with full-resolution fallbacks and valid appearance is saved to favorites. Moving unavailable items persists intent/placement/options without overwriting a valid saved title/icon with fallback data. Cache-update tasks and folder-preview refreshes skip unavailable targets.
- Foreground entry, relevant package/update callbacks, storage-event hints, and taps trigger worker-only revalidation. Foreground retries back off from 2 seconds to at most 60 seconds, stop when backgrounded or destroyed, and never authorize deletion. Model lifecycle cleanup unregisters the storage callback. Taps explain that the shortcut is being kept while the target is unavailable.

## Unverified requirements and residual risks

1. Full application compilation, all canonical tests, both real binding implementations, actual SQLite concurrency, icon serialization/rendering, lifecycle/retry scheduling, and the Lenovo storage scenario remain unverified. The candidate needs independent full-diff review and platform validation before being described as complete or ready for upstream submission.
2. Actual package installation UUIDs are persisted. Public/adopted-volume mapping has deliberately not been guessed or promoted to readiness evidence. Any unestablished association remains unresolved, and even a matching mounted volume would not authorize deletion or recovery without positive target resolution. Concrete adopted/public mapping and real storage callback delivery still require device evidence.
3. An external application's uninstall missed while the launcher was stopped is indistinguishable from unresolved storage absence through negative lookup alone. Such a row is retained conservatively until reliable removal evidence, explicit user deletion, or subsequent availability. No timer or boot/mount event resolves this ambiguity.
4. Concurrent grid migration, backup restoration, database reset, and package callbacks need platform race testing. The journal is tied to exact database incarnations, and reconciliation runs before and after migration, but copying rows into a different database while an event is being snapshotted is not established by the narrow tests.
5. Full-resolution folder fallback retention increases model memory and appearance-write I/O. Positive metadata batching avoids a full journal fsync per healthy loader row; remaining failure-path writes prioritize durability over throughput. Native performance profiling has not been performed.
6. Tombstones are retained indefinitely and no compaction policy is implemented. The reader rejects oversized or invalid journals conservatively. Atomic replacement and process-interruption behavior are tested; power-loss durability of the containing directory and Android filesystem implementations is not established by the Windows test.
7. AOSP has no downstream custom-label/icon subsystem in this revision. The new recovery paths preserve existing saved appearance rather than intentionally reassign it; broader non-native customization integrations and normal healthy app/theme updates are not validated by this branch.
8. The new explanatory resource has an English default only; ordinary upstream localization remains outstanding.
