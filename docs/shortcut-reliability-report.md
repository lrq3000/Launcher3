# Launcher3 shortcut reliability implementation report

## Status and scope

An integrated implementation candidate and one six-finding correction pass are present on `fix/preserve-unavailable-shortcuts`, based on authoritative Google revision `c612e6ece389f21c40f8cb9cd9a4b44239f00009` (`android17-release`). Independent review found the original `bcd0ab2a607c4e448eeb4cdcdb38f289b66473cc` tip NOT merge-ready. All six findings are addressed in source with observed narrow runtime RED→GREEN evidence; this does not establish platform readiness. This standalone Windows checkout has Soong definitions but no Android platform dependency tree, generated flag/Dagger classes, Soong build runner, or directly runnable canonical Launcher3 test environment. No APK, full application compilation, canonical test pass, device result, emulator result, Gerrit submission, or upstream acceptance is claimed.

Only ordinary `Favorites.ITEM_TYPE_APPLICATION` favorites are protected by the new recovery policy, including desktop, dock, and folder children. Corrupt intents, removed profiles, widgets, deep shortcuts, promise/restore placeholders, and invalid placement remain on their existing specialized paths. Ordinary applications with positive internal-storage AND exact-row history outside recovery retain normal missing-target policy; migration targets without sufficient exact-row history are provisionally preserved.

## Integrated behavior

- The actual receiver regression reproduced a synthetic uninstall after boot completion. The receiver now emits only availability/unavailability hints; boot completion is not uninstall evidence.
- `WorkspaceAvailabilityStore` keeps checksummed per-serial/package storage evidence and database/serial/item/component/insertion-generation-scoped recovery/removal state in no-backup storage. Journal version 2 reads version 1 legacy rows. Writes fsync a sibling and atomically replace the committed file. Incomplete siblings are ignored; corrupt/missing/unreadable metadata cannot authorize a negative-lookup purge. One canonical-path factory/private constructor shares mutable ownership and batching across regular and preview models; safety-critical evidence bypasses positive-observation batching.
- A one-row companion identity table gives each favorites database incarnation a token; a companion birth table associates each item ID with a journal-clock UUID/monotonic insertion generation. Fresh inserts reserve that generation durably before SQL mutation, then favorites and birth metadata commit together. Failure to persist birth reservation refuses insertion rather than permit identity reuse; aborted SQL writes consume harmless gaps. The numeric allocator, favorites columns, and database schema version are unchanged. Reset drops identity/birth metadata. Historical copies and migration ID renumbering preserve birth identity transactionally. Actual Android SQLite behavior has authored canonical tests, not an executed platform result.
- Real package callbacks are registered on the existing helper executor. Consequential events are journaled before model work can be discarded. Active loaders restart; shared event revisions are checked under the operation gate before committing loader deletions and before repository/legacy binding publication. Already loaded models use normal update tasks and retain the same item object.
- Confirmed uninstall durably records a profile/package insertion-generation cutoff BEFORE querying identity/favorites, then records exact snapshot rows where possible. A failed snapshot or unavailable identity leaves retryable evidence across disk reload; later insertions exceed the cutoff, while historical migrated rows remain eligible. Only the latest cutoff per profile/package is retained, not an unbounded event list or a forever-matching future-install tombstone. Reconciliation never inserts or recreates favorites and is idempotent across process death between journal and favorites writes. Positive target resolution never clears a removal. Lookup-based removals have a distinct task-factory entry point.
- Loader and update paths retain the exact intent/component during recovery, retain occupied cells and folder contents, and reactivate only the saved target. Recovery does not enqueue installation icons or insert a new row. Independent disabled bits survive a storage recovery update; normal non-recovery updates and explicit suspension/profile callbacks retain their existing authority.
- Ordinary favorites can read saved icon blobs; unavailable items bypass grouped generic icon replacement and package-cache purges. Valid cached appearance is retained when recovery completes. Folder children are loaded with full-resolution fallbacks and valid appearance is saved to favorites. Moving unavailable items persists intent/placement/options without overwriting a valid saved title/icon with fallback data. Cache-update tasks and folder-preview refreshes skip unavailable targets.
- Package refresh first identifies protected saved targets and checks registered activities without mutating cache. If any saved target is absent, destructive whole-package icon refresh is skipped; the app-drawer update also retains protected component-cache entries. Healthy refresh still precedes the normal app-drawer update. Deferred removal predicates capture immutable user/ID/component/generation keys on the model worker and perform no database or service queries on the UI thread.
- Foreground entry, relevant package/update callbacks, storage-event hints, and taps trigger worker-only revalidation. Foreground retries back off from 2 seconds to at most 60 seconds, stop when backgrounded or destroyed, and never authorize deletion. Model lifecycle cleanup unregisters the storage callback. Taps explain that the shortcut is being kept while the target is unavailable.

## Six blocking review findings: correction evidence

Each case has an individual command, `python tests/shortcutreliability/run_tests.py --finding N` for N=1 through 6; the default command runs all six. All six produced observed runtime assertion failures before the corresponding production correction, then passed after it. The first three independent fixes were committed as `b094bd4f90bf90670f136074b23ddf38850fe95a` (`fix(model): share journal ownership and bound update side effects`); the coupled identity/fence/migration correction and generation-aware UI refinement are committed with this report. Resolve the exact final tip with `git rev-parse HEAD`; no push or integration is implied.

1. **ID reuse — corrected at the production durability boundary; native allocator test unrun.** RED: `Finding 1: reused ID/component inherited the old uninstall tombstone`. GREEN exercises the real journal's durable generation allocation/reopen using the SAME ID and component, preserving the old removal while admitting the new incarnation. Additional store assertion refuses insertion when birth persistence fails. The canonical SQLite test closes/reopens actual DatabaseHelper and obtains the replacement ID from the real allocator, asserting that it repeats the old ID and has a new birth.
2. **Competing journal owners — corrected; executable shared-owner/batch/disk evidence.** RED: `Finding 2: second owner's uninstall was erased by the first owner's batch`. GREEN uses two real WorkspaceAvailability adapters against the canonical journal path, interleaves observation batching with the second owner's removal, flushes, then reads a fresh production store from disk. Production construction is private; test-only reflection obtains fresh-process readers.
3. **Migration snapshot race — corrected at the operation boundary; Android race test unrun.** RED: `Finding 3: callback snapshotted empty migration destination before copy`. GREEN uses the real fair operation gate and callback adapter, blocks the callback at a simulated empty helper destination, completes the copy, then verifies one exact row is snapshotted and reconciled. The canonical latch test uses actual ModelDbController helper switching and SQLite copy; only migration timing is controlled by a mock. Historical birth identity survives direct copies and migration renumbering.
4. **Failed snapshot loses uninstall — corrected; executable failure/restart/reinstall evidence.** RED: `Finding 4: failed snapshot lost the confirmed uninstall across restart`. GREEN covers query failure and unavailable identity, discarded callbacks, rapid remove/add, fresh disk ownership, repeated uninstall cutoff advancement, and later insertions surviving. The narrow favorites double uses production generation reservation but simulates SQLite birth storage; the canonical test exercises actual SQLite and a disk-reloaded journal.
5. **UI predicate queries — corrected; executable post-worker boundary evidence.** RED: `Service query after worker phase`, from the original captured predicate. GREEN forbids service/database queries after worker execution, changes database identity, and evaluates the saved predicate. Old membership remains stable; a new generation with the same ID/component does not match. Loader/ModelWriter populate runtime generation and the WorkspaceItemInfo copy constructor retains it for UI/drag copies. Actual platform binding remains unrun.
6. **Premature icon eviction — corrected at task/cache boundary; actual-cache test unrun.** RED: `Finding 6: package refresh erased the only durable saved-component icon`. The improved boundary cache evicts all package entries and rebuilds registered activities, rather than silently doing nothing. GREEN retains the only saved-target cache entry through an incomplete activity list and a fresh cache wrapper. Canonical coverage uses actual IconCache and its SQL database. Neither test establishes native process death/rendering.

## Lock ordering and insertion-path audit

One shared fair ReentrantLock is acquired before SQLite transactions, helper initialization/switch/copy, callback fences/snapshots, and loader commit/binding guards. Transaction wrappers retain it until SQL close. Callback code releases it before `availabilityChanged` or task dispatch acquires LauncherModel locks; it does not lock BgDataModel while holding the operation gate. Model worker publication can take its ordinary model locks inside the gate; removing the previous adapter/controller synchronized monitors avoids the reverse helper/model-monitor order. This argument is source-level plus narrow concurrency evidence, not proof against all Android runtime races. No production manifest declares an additional process; this is not a cross-process file-lock implementation.

Fresh insertion audit: DatabaseHelper.insertAndCheck covers layout parsers and ModelDbController.insert; ModelProxyProvider and ModelWriter both route there. Context-aware SQLiteTable.insert/insertOrReplace also stamp birth metadata and acquire the gate before transactions. GridSizeMigrationDBController uses an explicit historical-birth insertion when renumbering IDs. LauncherDbUtils.copyTable and GridBackupTable copy favorites/births atomically; default-column restore recreations retain the same IDs and existing companion mappings rather than being new installations. All `src` SQL insert sites and production SQLiteTable constructors were inspected; raw SQLite handles still rely on their owning initialization/migration scopes, not automatic interception of arbitrary SQL.

A local Python/SQLite characterization probe observed `database is locked` when an exclusive destination transaction read its attached source through a separate connection; reading the attached schema on the transaction-owning connection succeeded. The production copy uses that topology. This probe is not Android SQLite validation, and the authored canonical rollback/success test remains essential.

## Unverified requirements and residual risks

1. Full application compilation/type resolution, all 14 authored canonical regressions and the broader suite, both real binding implementations, actual Android SQLite concurrency, icon serialization/rendering, lifecycle/retry scheduling, and the Lenovo storage scenario remain unverified. The original review is not retroactively a review of this corrected tip. No new reviewer was invoked; coordinator assessment and platform validation remain necessary before integration/readiness claims.
2. Actual package installation UUIDs are persisted. Public/adopted-volume mapping has deliberately not been guessed or promoted to readiness evidence. Any unestablished association remains unresolved, and even a matching mounted volume would not authorize deletion or recovery without positive target resolution. Concrete adopted/public mapping and real storage callback delivery still require device evidence.
3. An external application's uninstall missed while the launcher was stopped is indistinguishable from unresolved storage absence through negative lookup alone. Such a row is retained conservatively until reliable removal evidence, explicit user deletion, or subsequent availability. No timer or boot/mount event resolves this ambiguity.
4. Concurrent grid migration, backup restoration, database reset, and package callbacks still need platform race testing despite the shared operation gate, preserved historical births, narrow callback-race evidence, and authored canonical latch/rollback tests. Coordination is in-process only; adding a production process would require a fresh ownership/locking assessment.
5. Full-resolution folder fallback retention increases model memory and appearance-write I/O. Birth reservation adds a journal fsync per fresh insertion and package protection adds a read-only activity query. Positive observation batching avoids a full journal fsync per healthy loader row; safety-critical writes prioritize durability over throughput. Native performance profiling has not been performed.
6. Exact tombstones, companion birth mappings, package cutoffs, and canonical owners can grow; only repeated removal events for the SAME profile/package are coalesced. No general compaction policy is implemented. The reader rejects oversized or invalid journals conservatively. Atomic replacement and interruption fixtures are tested; power-loss durability of the containing directory and Android filesystems is not established by Windows tests. Persistence failure cannot guarantee retention of an uninstall that could not be written; a new insertion is refused when its identity cannot be persisted.
7. AOSP has no downstream custom-label/icon subsystem in this revision. The new recovery paths preserve existing saved appearance rather than intentionally reassign it; broader non-native customization integrations and normal healthy app/theme updates are not validated by this branch.
8. The new explanatory resource has an English default only; ordinary upstream localization remains outstanding.
